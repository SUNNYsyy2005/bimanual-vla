# 2026-10-21 π0.5 实测复核：新轨迹生效延迟与回退

本次结论只针对 8099 的 π0.5 记录，按用户要求排除 8101。
读取了今天 26 份 8099 记录；重点核查 10:57:41、10:58:46、11:00:00、11:00:58。
只做离线分析与规划重放，没有修改运行中的控制器、GUI、模型或训练任务，没有发送机器人指令。

## 最重要的新发现

**除了模型原始输出的小幅锯齿，执行端还存在显著的新计划接替滞后。这是回退不能仅归因于模型的直接证据。**

在 11:00:58 运行的 generation 31、左臂关节2附近：

| 事件 | 相对该次记录起点 |
|---|---:|
| 观测采集 | 15.584800 s |
| 新结果返回 | 15.763386 s |
| d=5 的已承诺旧前缀结束 | 15.834800 s |
| 离线重放匹配的新计划起点 | 约 16.087446 s |

推理观测到返回约 **178.6 ms**；返回后到上述接替时刻又有约 **324.1 ms**；
观测到接替合计约 **502.6 ms**。其中约 **252.6 ms** 已超过 RTC 前缀保护区间。

起点不是从 generation 标签变化猜测的：标签变化时仍可能发布旧计划的保留段。
`replay_probe.py` 从记录的 q/v/a 重放对应原始 chunk，匹配所有12个关节的已发布段。
相邻几代的重建匹配误差小于 5e-8 rad；冻结旧预测的重放在下一计划真正产生不同输出前，
还继续匹配跨 generation 标签的实际发布轨迹。重建是约10 ms时间分辨率的离线推断，
日志没有直接记录内部 splice boundary 或每次准备耗时，不能把推断时间当作直接采集的内部事件。

代码对应：`bimanual_vla/deployment/servo.py` 的 `install_chunk()`：

```python
boundary = max(now + self._chunk_prepare_lead_s, self._committed_until)
self._chunk_prepare_lead_s = min(.5, max(
    self._chunk_prepare_lead_s, 2 * (time.monotonic() - prepare_started) + .02))
```

准备提前量初始50 ms；一次慢准备可以把它推高，随后不会随耗时恢复而下降，最高500 ms。
计算已经完成也仍会等到预约的未来边界。这是额外等待的代码机制，**不等于每次实际计算都花了324 ms**。
记录不足以回推是哪一次慢计算抬高了这个内部值。

## 固定输入对照：只提前交接，不改模型与运动限制

`handoff_counterfactual.py` 使用同一个 generation 31，保持：

- 原始预测、关节限位和夹爪转换相同；
- 起始 q/v/a 来自原始实际发布状态；
- 速度0.6 rad/s、加速度3 rad/s²、jerk60 rad/s³不变；
- 同一 `compile_chunk`、同一目标时间轴。

仅在已承诺前缀结束后的第一个10 ms规划采样点（15.837446 s）开始接替。
从该时刻往后450 ms，左臂关节2：

| 指标 | 原实际下发 | 提前接替的离线规划 |
|---|---:|---:|
| 共同起始位置 | 0.284906 rad | 0.284906 rad |
| 最低位置 | 0.199951 rad | 0.261176 rad |
| 回退幅度 | **0.084954 rad** | **0.023729 rad** |

这段回退减少约72%。起始速度 -0.149863 rad/s、加速度 -3 rad/s²，因此在相同限制下仍有一段制动回退，
不应要求速度瞬间反向。额外的大部分回退可以通过及时交接减少，**不需要先假定模型输出变好**。
这只是固定输入的规划对照，未纳入准备计算能否按时完成，也不是实机闭环或抓取成功率实验。
不能把72%推广到所有回退片段。

图：`handoff_counterfactual.png`。这是本次最值得优先处理的执行端问题。

## RTC 前缀位置有没有接错

检查真正启用 client_planner 前缀且包含 client_plan_id 的请求，排除启动/重置时无前缀的推理。
将前d步服务器绝对关节输出与同一未来规划时刻实际发布的计划样本比较，
仅纳入有对应10 ms采样的点（按计划时钟向下取样，不拿硬件反馈冒充计划前缀）。

最近四次的最大误差均小于 **3.8e-7 rad**，属于浮点数精度。
因此这些已核对的前缀没有证据表明发生了关节语义错误或错步连接。
但这不能证明新后缀及时生效；前缀对齐和新计划接替延迟是两个问题。

前缀到第一段新后缀的50 ms有限差分速度变化，按每个请求12关节最大值统计，P95为0.48–0.56 rad/s。
这是**模型位置序列隐含的速度变化**，不是机械臂实际瞬时速度跳变。
受约束前缀的位置匹配，并不自动约束新后缀的速度、加速度或更长时间运动方向。

## 原始输出与平滑效果

原始 chunk 内确实存在锯齿。例如11:00:00、generation 89、左关节2，源索引8/9/10：
`1.611058 → 1.650583 → 1.610881 rad`，相隔50 ms。
这些值是服务器已转回的绝对关节目标，不是逐步累加的增量；也不是机械臂实测加速度。
队列选择覆盖这段附近，但原始源点不等于规划器最终逐点到达的位置。

相同策略实例下，10:03:25开平滑和10:04:03关平滑的实际指令，统一到50 ms网格后，
最大关节位置二阶差分的P95分别约3.19和27.08 rad/s²。
这支持关闭平滑会暴露更多指令高频变化，但两次场景和RTC前缀来源不同，不是严格单变量A/B。
这些数值是发布指令差分指标，不能当成电机真实加速度或用于判断限幅实现违反约束。

相邻预测在同一未来时刻也会改变，但变化包含观测更新、规划前缀反馈和模型修正。
**不能仅凭这种差异就断言模型是回退主因。** 特别是新预测尚未生效的期间，实际动作仍可能来自旧计划。
原先先看相邻模型方向变化就解释回退的判断不充分，应以本次生效时间重建和固定输入对照为准。

## 机械臂是否一直追不上

以反馈采样时刻之前已发布的指令对齐，统计正常运动且未制动样本，每个样本取12关节最大误差：

| 运行 | 指令→反馈误差P95 | 选中参考→实际发布指令差距P95 |
|---|---:|---:|
| 10:57:41 | 0.0267 rad | 0.0578 rad |
| 10:58:46 | 0.0493 rad | 0.0751 rad |
| 11:00:00 | 0.0453 rad | 0.0672 rad |
| 11:00:58 | 0.0504 rad | 0.0790 rad |

第二列和第三列代表不同环节，不能相减或把第三列当作电机跟踪误差。
这些运行的规划速度达到0.6上限99%的运动样本占比仅0–0.23%。
当前记录不支持把这些回退主要归因于速度上限太小、机械臂长期追不上。
这也不意味着0.03–0.05 rad对精细抓取没有影响；缺少标定后的瓶子/末端位姿，不能给出厘米级抓取误差归因。

## 本次已实现的执行端修复

后续用户明确要求继续优化，已修改本机实际使用的 `servo.py` 与 `chunk_planner.py`：

- 准备预算改为最近实测耗时的1.25倍加一个发布周期，同时让历史高预算每次减半回落；下限两个发布周期，仍保留超时拒绝和旧计划继续运行的逻辑。一次慢计算不再永久锁定数百ms等待。
- 新计划仍基于原始绝对目标时间轴，在实际预约接替边界确定源索引，包含规划和提交所需时间，不把推理延迟与规划延迟重复加到源索引上。
- 保留段同时保留旧 generation/source_index；日志不再在计划安装时就把仍执行的旧前缀误标为新 chunk。
- `plan_timing` 记录计算开始/结束、取得提交锁、安装、预约接替、首次实际发布，以及对应源索引。结合 `model_commands.jsonl` 同 generation 的采集/返回时刻，可直接统计完整延迟。
- 保护前缀、q/v/a连续性、物理限位和跟踪保护均保留，未通过跳过安全约束缩短等待。

本地40份实测chunk离线编译耗时：中位数约11.15 ms、P95约11.48 ms（不含真机CAN锁竞争）。
假设历史准备预算已被抬到500 ms，在这些耗时下依次回落为250、125、62.5、31.25、约24 ms。
运行中的首次真实生效时间仍应以新增日志验证，不能把离线CPU结果当成实机总延迟保证。

验证：规划器/伺服、RTC客户端、机器人控制桥接和部署记录共 **139项测试通过**。
新增测试覆盖慢准备后的恢复、旧前缀来源保留，以及包含推理/准备/前缀保护时间的实际接替记录。
没有启动机器人运动；已运行中的旧客户端进程需要停止后重新启动推理，才能加载新模块。
