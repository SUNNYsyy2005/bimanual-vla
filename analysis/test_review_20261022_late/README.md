## 结论

小幅反向运动确实存在。举证的片段中，服务器原始绝对关节目标已经包含回退，规划后的指令和机械臂反馈随后都出现回退。不能把这些例子解释为执行端单独选错旧目标；但服务器输出包含 trained RTC 条件，尚不能区分模型固有预测问题、前缀条件的分布偏差和采样问题。

上次重试预约门控已加载：10:44、10:45、10:46 的监控中有 `RTC prefix waits for deferred chunk ... installation`，说明重试期间阻止了新的旧前缀预约。六轮 501 次实际新代际接替中，返回后再等至少 300 ms 只有 1 次（10:45 的 generation 40，318 ms，准备过程中多次重试）。因此旧的额外整段等待已经不是普遍现象；仍有短重试，不能声称全部消失。

## 回退的直接证据

10:47:28，generation 31，右关节 2：

| 原始 chunk 点（从 1 开始） | 关节目标 |
|---|---:|
|第 6 点，最后一个已约束前缀点|0.176833 rad|
|第 7 点，新预测|0.175305 rad|
|第 8 点，新预测|0.157763 rad|
|第 9 点，新预测|0.213091 rad|

这个回退已经存在于服务器返回值中，未经过客户端平滑。原始目标是绝对角度，未做累计求和。该轮所有 80 个有效上传前缀与返回前六点的最大元素误差均低于 1.8e-7，说明这个例子的前缀数值传递/还原正常，不是前缀被错误累加或替换。

该轮 +2 s 之后，右关节 2 前缀末两点仍在增加（差 >0.0005 rad）的 70 个请求里，40 个请求的随后三个预测点至少有一个比前缀末点低 0.01 rad。这个条件统计不等于 40 次实际抖动，也不等于所有回退都不符合任务，但说明边界后回退并非孤例。

实际下发轨迹 +8.89→9.44→9.64 s 为 0.1143→0.1782→0.1533 rad，实际反馈紧跟。见 `reversal_104728.png`。图中每条虚线是不同返回 chunk 按其原始时间轴绘制，较远未来的旧预测未必实际执行，不能把它们与当时指令的差距当作机械臂跟踪误差。

六轮采用一致的“50 ms 网格、三极值总跨度 ≤1.5 s、两侧幅度均 ≥0.02 rad、排除 hold/启动”的诊断，分别检出 12、12、10、0、2、5 个指令往返事件。它不是高频机械振动测量，也会包含正常任务反向；10:45 检出 0 不代表完全无抖动。关键例子的同向下发/反馈及原始预测反向，比单纯计数更能定位来源。

10:44、10:45、10:47 的速度饱和比例为 0（运动样本中最大关节速度达到配置 0.6 rad/s 的 99%）；没有依据把提高速度上限作为这三轮的主要修复。关节跟踪误差较小也不能直接保证夹爪端点的毫米级精度。

视频显示任务画面和视角确实变化：10:44 右腕从约 +16 s 起主要看到背景/天花板，俯视相机仍可看到瓶子；10:47 +24 s 也有类似右腕视角变化。它们并非相机冻结的证据，也不能证明模型识别了抓取偏差。图像软件读帧时间戳不能替代传感器曝光时刻。

## 8102 必须单独解释

10:50:28 / 10:51:13 关闭异步推理及 RTC，结果延迟中位数分别 966 / 871 ms，实际请求间隔 1.60 / 1.68 s。有效下发约 2.7 / 3.6 s，hold 约 3.4 / 4.9 s。同步等待造成明显停走，不能认为 GUI 写 4 Hz 就实际达到 4 Hz。

这两轮虽然 GUI 同样选 Ruckig，但记录中 `plan_id` 为空，走逐点跟踪；代码中整段 `install_chunk` 受 `planner_prefix_enabled` 控制。它们不是 8099 多点规划的等价执行路径。运动跟踪误差 P95 约 0.148 rad，速度触顶比例约 68% / 53%，原始参考与执行指令也相差很大。因此这两轮既有更慢的推理，也有不同的执行模式，不能直接归咎于同一个 RTC 回退问题。

## 后续优先级

1. 用同一观测和 checkpoint 离线比较无前缀、原规划前缀、训练真实前缀，重点测前缀末点后的反向幅度和速度连续性，区分模型预测与前缀条件问题。仅更换端口且同时改变异步模式不是有效对照。
2. 针对远程服务的当前延迟重新评估六步前缀是否过长，同时保留尾部延迟超限统计。不能只因中位数快就无条件缩到三步；10:43 和 10:46 存在较大尾部。
3. 继续定位 4 Hz→约 3.3 Hz 的主线程时间空档与少量重复规划重试；保持轨迹平滑，避免通过关闭伺服或放宽速度掩盖回退。
