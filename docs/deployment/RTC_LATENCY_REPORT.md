# RTC 延迟标定（2026-10-19）

数据来源：`deployment_runs/*/metadata.json`、`model_commands.jsonl` 和
`trajectory.jsonl`。共 93 次运行、23,118 条具有有效单调时钟起止时间的
推理记录，其中 19,924 条 accepted。记录日期为 2026-09-29、09-30、10-08。

## 统计口径

- 使用客户端单调时钟计算 `arrived_monotonic - captured_monotonic`。
- 排除未接受、带 error 的请求和各次运行第一条请求，得到 19,854 条记录。
  第一条统一排除只是减少启动阶段影响，不代表已识别所有冷启动。
- 将 model generation 与 trajectory 的 command_generation 对齐，选择
  首次 `command_sent=true` 且非 hold 的命令，计算采集到首次下发时间。
- 模型推理耗时取独立记录的 model_inference_ms，不把它等同于端到端延迟。
- 不用客户端与服务端墙钟相减推断单向网络耗时，避免时钟偏移干扰。
- 首次下发时间不是物理机械臂到达目标的时间，也没有额外加入相机图像年龄。
- 被拒绝请求不包含在这些覆盖率中；这些是已接受请求的经验分布，不是可靠性保证。

## 配置建议

以当前历史数据作为初始依据，建议 `rtc_training_max_delay=10`，训练随机
采样 0–10 步干净前缀。若部署链路更不稳定，可选 12 步；不建议仅为覆盖
约 1 秒的偶发尖峰而直接把常规训练上限扩大到 20 步。

启用 trained RTC 时，运行时 `rtc_execution_horizon` 建议同步设为 10
（训练上限取 12 时设为 12）。最新五次记录的 execution_horizon 为 6；
当前服务端会拒绝预测延迟大于 execution_horizon 或 training_max_delay 的请求。
客户端目前以历史采集到结果到达耗时估计下一次延迟，并非预知本次实际延迟；
上表的实测覆盖率不能当作服务端一定接受/拒绝请求的概率。

本次只分析历史日志，未修改训练或部署默认参数。上述记录来自旧部署链路；
更换 checkpoint、启用训练 RTC 或新的 100 Hz Ruckig 伺服后应重新测量。

## 处理链路排查

进一步核对发现，`arrived_monotonic` 在 `AsyncPolicyInference.poll()` 中记录，
代表控制循环接纳结果的时刻，不是网络接收时刻。真正的客户端 infer 返回边界
为 `_client_transport_timing.response_received_monotonic`；该边界也在解包之后。
因此前文“结果到达”应理解为“控制循环接纳结果”。

10 月 8 日同一组 1,943 条记录的分段统计如下；各行分位数不能直接相加。

| 分段 | P50 ms | P95 ms | P99 ms |
| --- | ---: | ---: | ---: |
| 观测时间戳到 snapshot/launch 记录 | 0.76 | 16.40 | 25.76 |
| launch 记录到客户端 infer 调用边界 | 6.44 | 12.36 | 14.50 |
| 客户端 infer 返回到控制循环 poll | 24.29 | 47.02 | 48.95 |
| poll 到首次非 hold 命令下发（1,916 条） | 16.80 | 27.95 | 37.06 |
| 服务端输入变换 | 1.13 | 1.35 | 1.98 |
| 服务端 batch/设备传输发起 | 15.09 | 15.89 | 17.32 |
| 服务端 Observation 构造/图像归一化 | 12.56 | 13.35 | 16.13 |
| 服务端 sampler | 74.52 | 74.91 | 75.58 |
| 服务端采样后处理 | 5.34 | 5.97 | 6.70 |
| RTC 锁等待 | 0.002 | 0.002 | 0.003 |
| RTC prepare | 0.40 | 0.47 | 0.53 |
| RTC finalize | 0.25 | 0.29 | 0.36 |
| 客户端 RTT 减服务端模型处理（未拆分） | 93.09 | 205.56 | 295.02 |

按单个请求先求和再统计，首次下发延迟减去 sampler 耗时和未拆分的非模型
RTT，剩余可归入处理/调度的时间 P50=88.68 ms、P95=119.97 ms（1,916 条）。
这不是可全部消除的开销。JAX 的异步设备执行也意味着表中阶段不能直接解读为
GPU kernel 的精确归属。

### 已定位的原因

1. 客户端每 50 ms 轮询一次完成的推理任务。返回后等待的 24/47 ms 分布
   与该调度机制一致。新 Ruckig 线程只提高执行频率，并未改变这段 20 Hz
   推理结果轮询。后续优化应保持模型时间轴与唯一执行线程，不可简单增加发送。
2. `launched_monotonic` 在 snapshot 完成时记录，但实际线程提交在本轮控制
   执行/记录之后。6.44 ms 的差值包含这段本地等待、线程调度和 build_observation，
   不能解释为纯线程切换耗时。
3. 服务端 109 ms 模型计时并非纯 sampler：约 29 ms 在采样前，5 ms 在采样后。
   约 15 ms 的 batch/dispatch 和 13 ms 的 Observation 阶段是进一步优化候选；
   输入 transforms 和 RTC 锁不是主要耗时来源。
4. 当前 Conda 安装的 `openpi_client.websocket_client_policy` 只执行 pack、
   send、recv、unpack，没有导出各阶段计时。全部 1,943 条日志中的
   client_pack_ms/client_send_ms/client_wait_response_ms/client_unpack_ms/
   request_bytes 均为空。项目虽预留这些字段，但没有获得实际测量。
5. 请求图像由 NumPy 原始字节经 msgpack 传输，WebSocket compression=None。
   仅三张 424×240 RGB 图像和 state 的模拟包约 916 KB，改为三张 224×224
   约 452 KB。历史记录不含实际 request_bytes 或 preresize 开关，不能确认
   每次请求究竟使用哪种尺寸。

本机轻量序列化实验（100 次、当前 dual_arm Conda、合成同尺寸图像、无网络）
中，916 KB 包的 pack P50/P95=0.065/0.273 ms，unpack=0.029/0.209 ms；
452 KB 包分别约 0.035/0.038 ms 和 0.018/0.019 ms。只说明当前空闲环境下
原始序列化本身不需要几十毫秒，不能排除历史负载下的 GIL/调度或服务端开销。

### 下一步优先级

先在实际使用的 WebSocket 客户端增加本机单调时钟的 pack/send/recv/unpack、
包大小和请求图像尺寸计时；服务端对应记录解包、推理前排队、响应打包及发送。
再用同一模型比较原图与已有 `--preresize-policy-images` 路径，保持其他设置一致。
最后再决定是否调整结果接纳调度、合并 JAX 输入处理或优化网络。

目前无法从历史日志把剩余 93 ms 唯一归因为网线、Wi-Fi、服务器排队或线程争用。
本次未连接远端服务、未启用实机、未修改控制程序与依赖。

## 后续优化实现与验证

已在后续修改中将固定 20 Hz 完成轮询改为事件唤醒；上面的固定轮询分析描述
的是优化前行为。结果接纳仍在控制线程进行。Ruckig 模式在接纳后立即唤醒一次
参考刷新，重新获取反馈、执行授权和安全检查，由既有伺服线程按 100 Hz 下发。
普通 20 Hz 时间轴不重置；off/legacy 后端保持原命令周期。

补齐了客户端编码/发送/等待/解码计时，以及服务端解包、处理、上次响应编码
与发送计时（带 generation 关联）。网络残差仍称为 unattributed_rpc_ms，
不把服务器响应处理、线程调度等未测部分直接视为网络耗时。

找到的 9 月 29–30 日原会话记录还确认：客户端预缩放曾令模型中位数从
154.0 降到 137.8 ms；堆叠上传曾从约 154 ms 变慢到 158 ms，已回退。
本次保留现有预缩放选项，没有重新引入堆叠上传或 JPEG 压缩。

优化目标是扣除实际网络传输后，从观测准备到首次下发的处理链路不超过
150 ms。当前日志仍不能独立确定纯网络传输时间，因此没有将历史残差扣除
后宣称真实部署已达标。

不连接机器人/GPU/远端服务，不包含真实相机获取、完整控制器安全检查和 CAN。
